# Organisation hierarchy

Aggregator orgs form a tree under the network root. Each org also carries a `known_as` value, which says what the org is known as ("State", "District", "Aggregator"). Each parent org defines the values for the orgs directly under it. Where an org sits comes from its parent, not from its `known_as`.

## Depth

- `organisations.depth`: the root is 0, an org directly under it is 1, a child of a depth-N org is N+1.
- The store sets `depth` on create and on move. A `BEFORE INSERT` trigger fills it from the parent when a writer does not send it. A CHECK ties depth 0 to the root.
- `scripts/sql/organisation-verify.sql` (gate V9) checks that every org's depth is its parent's depth + 1.

## Limits

Set in the instance config under `aggregator.organisation.hierarchy`:

| Setting          | Meaning                                                                               | Default |
| ---------------- | ------------------------------------------------------------------------------------- | ------- |
| `max_depth`      | The deepest an aggregator org can be. 1 keeps every org directly under the network.   | 1       |
| `max_children`   | The most direct child orgs any org can have, the root included. Unset means no limit. | unset   |
| `max_total_orgs` | The most aggregator orgs in the instance.                                             | 50      |

- Counts include `pending` and `active` orgs. Rejected and deleted orgs do not count.
- The Default org is not counted, is never a parent and is never moved.
- An org can take a child when it is the root or an active non-Default org, its depth is below `max_depth`, and it has fewer children than `max_children`.
- Lowering a limit leaves existing orgs as they are. New creates, revivals and moves are refused until the counts are within the limit. The API logs the counts at boot (`orgTree.bootCheck`): a warning per kind, and an error when the total is over `max_total_orgs`, because that closes self-registration.

## `known_as`

Each org defines the "known as" values for its direct children. There is no instance config for them and no depth rule.

- The table `org_known_as` holds each org's list, one row per value: `org_id`, `key`, `name`, `is_default`, `position` (the list order), `created_at`, `updated_at`. The primary key is `(org_id, key)`; at most one row per org is the default, and names are unique per org, ignoring case. The rows are deleted with their org. The root has a list too; it applies to top-level orgs. The Default org has none.
- On the wire a list is `known_as_values`: entries `{ key, name, default? }`. Reads include it only when asked: `GET /v1/org/read/:id?fields=known_as_values` adds the org's list (`null` when the org cannot have child orgs: it is at `max_depth`, or it is the Default org), and `GET /v1/org/hierarchy?fields=known_as_values` adds the network's list. An unknown name in `fields` answers 400 `SCHEMA_VALIDATION`. No other response carries the list. The console shows the list editor only when the list is not `null`.
- A list has at most 20 entries, unique keys and at most one `default` entry. A name is 1 to 60 characters.
- The owner types only the name. The API makes the key: the name transliterated to Latin (`any-ascii`), lower-cased, other characters turned into `_`, `v_` in front of a leading digit, cut to 64 characters. An empty result becomes `value_<n>`, and a key already in the list, or in the list being replaced, gets `_2`, `_3`, and so on. A saved entry sends its key back and keeps it, so renaming an entry changes the name every child shows and nothing else.
- `organisations.known_as` holds a key from the parent's list, or the built-in `aggregator` ("Aggregator"). The name shown is the parent's row for the key, read with a join on `(parent_id, known_as)`; a key the parent does not have reads as "Aggregator". The Default org is always "Aggregator".
- The choices for a child are the parent's list, or only `aggregator` when the list is empty. `GET /v1/org/read/:id?fields=known_as_options` returns them to the owner of the parent (`null` for anyone else).
- A child's `known_as` is set by the owner of its parent: the network admin for a top-level org, because it owns the root. The owner of the child is emailed when it is not the one who made the change. When the parent is inactive, nobody can change its children's values; they stay as they are.
- A new org, and a rejected org that registers again, gets the parent's `default` entry, else `aggregator`.
- An org that holds `aggregator` keeps it: neither a move nor a list edit resets it.
- A move keeps the moved org's key when the new parent's list has it; otherwise the org takes the new parent's default, else `aggregator`. Orgs below the moved org keep theirs.
- Saving a list replaces the org's rows in one transaction. A value whose name, default and position did not change keeps its timestamps.
- When an owner removes a value from its list, the children that use it take the new default, else `aggregator`. Children in every status are reset, the Default org is skipped, and their `updated_at` does not change. No email is sent for list edits.
- Changing an org's `known_as` never moves it.
- At boot the API logs how many orgs hold a key that is neither in their parent's list nor `aggregator` (`orgTree.bootCheck`).

## Writes

All tree writes (create, revive of a rejected org, move, a change of an org's `known_as`, a change of an org's `known_as_values` list) take one transaction-scoped advisory lock (`aggregator-dpg:org-tree`) as their first statement, so the limit counts and the cycle check are exact.

| Route                               | Who                                                                                                                                  | What                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /v1/orgs/create`              | Self-registration (service)                                                                                                          | Optional `parent_id` (root when omitted). Refusals: 400 `parent_id` invalid; 409 `ORG_DEPTH_LIMIT`, `ORG_CHILD_LIMIT`, `ORG_TOTAL_LIMIT`. A rejected org registering again is revived under the parent picked now, under the same checks.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `GET /v1/orgs/parents`              | Service                                                                                                                              | Parents that can take a child now, and `accepting` (false when registration is closed by the limits).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `PATCH /v1/org/metadata/update/:id` | Org owner                                                                                                                            | Changes the org's details. It does not take `known_as` or the parent.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `PATCH /v1/org/known-as/update/:id` | Owner of the parent org for `known_as`; org owner for `known_as_values` (network admin for a top-level org, and for the root's list) | The body has exactly one of two fields. `known_as` sets the org's value to one of the parent's choices (400 `SCHEMA_VALIDATION` otherwise); 403 when the caller does not own the parent; 409 `CONFLICT` for the Default org, a rejected org, or an org moved while the request ran. The org's owner is emailed when it is not the caller. The current value answers 200 with no write and no email. `known_as_values` replaces the org's list and answers with the org and the saved `known_as_values`, keys filled. New entries send only a name; a sent key must already be in the list (400 `SCHEMA_VALIDATION`, `fields.known_as_values: unknown_key`). Children whose value leaves the list are reset. 403 when the caller does not own the org; 409 for the Default org. |
| `PATCH /v1/org/parent/update/:id`   | Network admin                                                                                                                        | Moves a pending or active org (and everything below it) under a new parent. The body takes no `known_as`; the moved org's value follows the rule above. Refusals: `ORG_PARENT_CYCLE`, `ORG_DEPTH_LIMIT`, `ORG_CHILD_LIMIT`, 409 `CONFLICT` (not movable, or the row is busy). The moved org's owner is notified.                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `GET /v1/org/parent/options/:id`    | Network admin                                                                                                                        | Every candidate parent with whether the move would succeed and why not.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `GET /v1/org/hierarchy`             | Network admin                                                                                                                        | The network, the limits and the total orgs; with `fields=known_as_values`, the network's list too.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

## Reads below an org

An owner reads, view-only, every org and coordinator below the orgs it owns (`services/authz/view-scope.ts`). Writes keep the owned reach. Contacts below are masked, and those reads log `relation: 'below'`. RBAC roles held in an org do not apply below it.

## Upgrading an existing instance

No manual data step is needed. Migrations 0032 and 0034 run at API boot and are safe while older pods still serve (migrations after the 0023–0029 instance upgrade run at boot; see `migration-guards.ts`).

- **Data.** `known_as` is added with the default `aggregator`, so every existing org is "Aggregator" without a table rewrite. `depth` is filled from the parent chain: every org directly under the root gets 1. The migration is idempotent. `scripts/sql/organisation-verify.sql` gate V9 checks the result.
- **Data (0034).** Creates the empty `org_known_as` table and sets every org's `known_as` to `aggregator`, without changing `updated_at`. Every org shows "Aggregator" until the owners define their lists. The migration is idempotent. While older pods still serve, they can write keys from the instance config; the boot check counts them, and they read as "Aggregator" until someone sets the value.
- **Config.** An instance config without `aggregator.organisation` keeps a flat tree: every org directly under the network and at most 50 orgs. Add the block only to use more depth or a different total. The API ignores an `organisation.known_as` block and logs a warning at boot (`orgTree.bootCheck`, check `known_as_config`); remove the block.
- **Instances already over a limit.** Existing orgs are kept, with their coordinators, as they are. The API logs `orgTree.bootCheck` with the counts; a total over `max_total_orgs` is logged as an error (`registration: "closed"`). Self-registration of new orgs is closed (`accepting: false`, `409 ORG_TOTAL_LIMIT`), and so are revivals and moves that break a limit. Approving an org that is already pending is not limited. Coordinator registration into existing orgs is not affected. **Release checklist:** count the instance's pending and active orgs (the Default org excluded) before upgrading; if there are 50 or more, set `max_total_orgs` above that count first, or self-registration closes on the first boot.
- **Rollout order.** Deploy the API before the web app. Older API pods insert orgs without `depth`; the `BEFORE INSERT` trigger fills it. Older web pods work with the new API: the new response fields are additive and `parent_id` on `POST /v1/orgs/create` is optional. The new web app needs `GET /v1/orgs/parents`, so against an older API the org registration form shows an error and a retry button.
- **RBAC edge.** `policy/rbac/edge/routes.json` adds `GET /v1/org/hierarchy`, `GET /v1/org/parent/options/:id`, `PATCH /v1/org/parent/update/:id`, `GET /v1/orgs/parents` and `PATCH /v1/org/known-as/update/:id`. Where the edge policy is enforced, ship the updated policy bundle with the release; until then the edge refuses these routes.
- **Rollback.** The columns, trigger and CHECK stay. Older code ignores the columns, and the trigger fills `depth` on its inserts. Orgs placed under another org keep that parent.
