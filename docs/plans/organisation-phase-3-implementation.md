## 0. Scope

**In this phase (one PR into `feature`, several commits, §8):**

1. Migration `0028_organisations.sql`:
   - rename `aggregator_orgs` → `organisations` (ids kept), `display_name` → `name`, `owner_user_id` → `org_owner`;
   - add `org_type`, `parent_id`, `url`, `locations`, `legal_name`, `gst_number`;
   - seed the **NF root**, its **network-admin** account and the fixed **Default** org;
   - `users.parent_org_id` → **`users.org_id`** (required for coordinators; the Default org when there was none);
   - move `url` / `locations` / company / GST from coordinators to their org (adoption rule), keeping non-adopted values in `users.legacy_org_details`;
   - `registration_invites.parent_org_id` → `org_id`;
   - tenant tables gain **`org_id`**.
2. The **hierarchy flag is removed**: org routes, the org dropdown and the invite pages are always on. `ORG_HIERARCHY_ENABLED` is ignored with a `warn` for one release (review A3).
3. Responses render org details **from the linked org**, falling back to `legacy_org_details`. Profile PATCH of org details → `409 ORG_DETAILS_READ_ONLY`.
4. Coordinator registration stops storing org details (accepted and ignored for one release, review R2).
5. Every org lookup is scoped to `org_type = 'aggregator'` (the NF root is never selectable, never an owner match).
6. Pre-flight and verify SQL for 0028; the boot guard covers 0028.
7. Tests (unit, integration from 0026 and from 0022, browser) and doc updates.

**Not in this phase:**

- Consent, `agg_for`, `actor_type`, `alternate_phone`, `contact_extra` removal, `invite_id`, the enum rename, the remaining `aggregator_*` TypeScript names: Phase 4.
- Org editing (`/v1/org/*`), network-admin login, the owner console: Phase 5.
- `known_as` and the optional `limits` config: deferred to Phase 5, where they are first used (§9, D3-9).
- The operator tool `scripts/user-org-migrate.sh`: its own PR in the train.

**Unchanged:** tokens, Keycloak, Signals payloads, every response field name. The intended visible changes are listed in §7.

## 1. Migration `0028_organisations.sql`

**Frame:** the same as 0027 (`0027_users.sql` lines 1–97, 363–365):

- save and restore `lock_timeout` / `statement_timeout`;
- `pg_advisory_xact_lock(hashtext('aggregator-dpg:0028_organisations'))`;
- run as the table owner;
- the `pg_temp.ren_*` helpers;
- `LOCK … IN ACCESS EXCLUSIVE MODE` on `users`, the org table **under either name** (`coalesce(to_regclass('public.organisations'), to_regclass('public.aggregator_orgs'))`, as 0027 U1 does), `registration_invites`, `contact`, `user_identities` and the five tenant tables;
- **"first run" is captured before the rename** (as 0027 U2 does) and every data step is gated per row (`org_type IS NULL`, the column still existing), because M2 renames the table inside the same run;
- every step idempotent (a re-run is a no-op);
- no `BEGIN` / `COMMIT`.

The journal `when` is `1791300000000`, and the boot guard's `TRAIN_LAST_WHEN` moves to it (§4).

`users_role_shape_chk` names `parent_org_id`, `url` and `locations`, so dropping those columns would silently drop it. M8 therefore starts with an explicit `DROP CONSTRAINT IF EXISTS users_role_shape_chk`, and M12 re-adds it (review R9).

**`updated_at` is never bumped** (review A9): `users_set_updated_at` is disabled around the data steps (the `0025_contact.sql:474/517` pattern). `aggregator_orgs` has no such trigger today, and the one added in M12 is created after the data steps.

## 2. Drizzle schema (`packages/db-schema/src/schema.ts`)

- `orgTypeEnum`; `organisations` table (TS export `organisations`, plus `aggregatorOrgs = organisations` as an alias until the Phase 4 naming commit, the same approach as `aggregators = users`). Property names follow the columns: `name`, `orgOwner`, `orgType`, `parentId`, `url`, `locations`, `legalName`, `gstNumber`, `createdBy`, `updatedBy`. Extra config in the array form.
- `users`: `orgId` replaces `parentOrgId`; `url` and `locations` removed; `legacyOrgDetails` added; `contactExtra` typed `Pick<BecknContact, 'alternatePhone'>`.
- `registrationInvites`: `orgId`.
- Tenant tables: `orgId: uuid('org_id').notNull().$defaultFn(() => sql`NULL`)`, so reads are non-null and inserts may omit it (the M14 trigger fills it).
- Row types: `OrganisationRow` / `NewOrganisationRow`; `AggregatorOrgRow` kept as an alias.

### 3.2 `ensureRootOrganisation()` at boot

Runs in `server.ts` **on every boot, whether or not `RUN_MIGRATIONS_ON_BOOT` is set** (existing instances migrate through the operator tool), after `getNetworkConfig()` and before `listen`, under a session advisory lock. Idempotent; counts-only logs. **A failure logs an error and boot continues** (review R8): nothing in Phase 3 depends on the root's owner. It reconciles the NF root and the Default org with config:

| Value                    | Source (first present wins)                                                                                                                                           |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| NF `slug`                | network config `brand.url_slug` → keep current                                                                                                                        |
| NF `name`                | `aggregator.legal_name` → `aggregator.name` → keep current                                                                                                            |
| NF `legal_name`          | `aggregator.legal_name`                                                                                                                                               |
| NF owner (network admin) | the **first `ADMIN_EMAILS`** entry (the env already used for approval routing; the unused YAML `aggregator.admin_emails` is not read) → keep the placeholder (`warn`) |
| Default org owner        | **`DEFAULT_ORG_OWNER_EMAIL`** (new optional env, D3-6) → the network admin                                                                                            |

**Owner accounts.** For each owner email: find or create the contact (reusing an existing person, plan risk row 3), find or create its `admin` account (`linkAdminAccount`), point the org's `org_owner` at it, then delete the previous admin account when it owns nothing else (the placeholder's contact is then collected by `contact_gc`). A slug that another org already holds is not applied (`warn`), so boot never fails on config.

**Keycloak (D3-4), mirroring org registration:**

- **Groups:** for the NF root and the Default org, when `kc_group_id` is NULL, create the group `org-<slug>` with `{org_id, display_name}` attributes (as `aggregator-orgs.ts:462`) and store its id.
- **Owner users:** for each configured owner email (never the placeholder), look the Keycloak user up by email. An existing user is **reused as it is** (never disabled or modified); otherwise a **disabled** user is created, as org registration does (`aggregator-orgs.ts:480`). Its subject is recorded in `user_identities`, and the user is added to the org's group. No `org_owner` role and no enabling: owner login is Phase 5.
- **Failures** (Keycloak down, a conflict) log a `warn` and are retried on the next boot; the database side is reconciled first and never depends on Keycloak.
- An owner change never deletes the previous owner's Keycloak user (it may be a person with other roles); it is only removed from the group.
- The NF group keeps its first name if the NF slug later changes (the name is a label; lookups use `kc_group_id`).

**Known limit (review R8b):** a contact created here has an email and no phone. Contact ids are derived from `(email, phone)`, so if that same person later registers as a coordinator or org owner with a phone, the email-uniqueness check answers `USER_EXISTS` / `OWNER_ALREADY_REGISTERED`. The network admin is an operator address, so this is documented rather than handled; Phase 5's admin login revisits it.

### 3.4 Rendering a coordinator (target model §4.3)

`aggregator-store` reads join the coordinator's org (one `LEFT JOIN organisations` in `selectJoined`):

| Domain field                                               | From                                                                                                                                                                     |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `url`, `locations`, `contact.company`, `contact.gstNumber` | the org's value; **when the org's is empty**, the coordinator's `legacy_org_details` key; else `null` / `[]` / absent (as today for a coordinator who never entered one) |
| `name` (→ `org_name`)                                      | `signalstack_org_name`, as today (no dedupe, D3-11)                                                                                                                      |
| `parentOrgId`                                              | `org_id`, Default included (D3-6)                                                                                                                                        |
| `isDefaultOrg` (new)                                       | whether `org_id` is the Default org (for the registration form rule and routing)                                                                                         |
| everything else                                            | unchanged                                                                                                                                                                |

Writes: `create` takes `orgId` (required) instead of `parentOrgId`, and `legacyOrgDetails` (Default registrations only) instead of `url` / `locations` / company / GST. `UpdateAggregatorPatch.parentOrgId` is removed (a `null` would now violate the CHECK). The Signals upsert is unchanged.

### 3.5 Tenant `org_id` (D3-5)

The M14 trigger fills `org_id` on every insert path, including the sixth one the plan missed (`apps/worker/src/jobs/bulk-finalise.ts:160`, `onboarding` from a bulk upload) and the anonymous public-link submit, where the user is known only through the link. **No store or route changes for inserts.** The Drizzle columns are typed optional on insert.

Accepted consequence: a row's `org_id` is the user's org **at insert time** (the plan's rule). The link-rollup unique key `(user_id, link_id, period_start)` is unchanged: a user's org changes only through Phase 5's move, and `onboarding` rows are per user anyway.
