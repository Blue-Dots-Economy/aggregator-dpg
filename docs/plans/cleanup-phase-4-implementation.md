## 4. Code changes

### 4.1 Schema and shared types

- `packages/db-schema`: `consentRecord` (table `consent_record`, `userId`, `orgId`, `validTill`); `users.serves`, `alternatePhone`, `inviteId`; drop `consent`, `type`, `actorType`, `contactExtra`, `inviteEmail`, `aggregatorActorTypeEnum`; `registrationStatusEnum`; `onboarding.signalstackOrgSlug`; `campaignPiiAudit.actorSignalstackOrgId`; `organisations.state` gone. Naming per **⚠ D4-7**.
- `shared-primitives`: `ActorTypeSchema` stays (the API still returns `actor_type: 'aggregator'`); `RegistrationPayloadSchema.type` unchanged (request contract).

### 4.2 Consent in one transaction (F5)

- `packages/consent-ledger`: input `{ subject: { userId } | { orgId }, network, brand, termsVersion, privacyVersion, source, validTill? }`; `recordRegistrationConsent(input, executor?)` writes on the caller's executor when given (the singleton handle otherwise, for bulk attestations); subject strings `'user'` / `'organisation'`. A read method `latestRegistrationConsent(userId)` for the profile (A19). Memory / testing fakes follow; `buildConsentRecord()` defaults change.
- `aggregator-store.create()` / `aggregator-org-store.create()` take an optional `consent` input and write the ledger row **inside** their existing transaction (after the user / org insert). A ledger failure rolls back the contact, the account and the row together: the compensating `deleteById` on the consent path goes away; `CONSENT_WRITE_FAILED` and the fail-closed contract stay.
- Keycloak-failure and stale-prune deletes still happen after commit: the ledger row stays, unlinked (P4-3, **⚠ D4-5**).
- Org registration stores the request's `valid_till` on its ledger row (**⚠ D4-4**).
- Bulk-upload attestation: `subject: { userId }`, unchanged `source`.
