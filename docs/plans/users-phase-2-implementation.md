## 0. Scope

**In this phase (one PR into `feature`, several commits, §8):**

1. Migration `0027_users.sql`:
   - rename `aggregators` → `users` (ids kept), `org_slug` → `signalstack_org_slug`, `name` → `signalstack_org_name`;
   - add `user_type`, and admin rows for org owners;
   - add `user_identities`, and `aggregator_orgs.owner_user_id`;
   - drop `aggregator_orgs.contact_id` / `owner_kc_sub`;
   - tenant tables `aggregator_id` → `user_id`;
   - recreate every DB function that names a renamed table or column.
2. Drizzle schema, stores, routes and worker queries for the new names. **No response, token, Keycloak or Signals change.**
3. A provider-neutral identity store (`user_identities`), recorded at the same points the abandoned `app_user` work used.
4. The org-delete helper (frees the owner's contact; keeps a Keycloak user shared with another org).
5. The **boot guard** and the **foreign-migration guard** in `db/migrate.ts`.
6. Pre-flight and verify SQL for 0027 (`scripts/sql/users-{preflight,verify}.sql`).
7. Tests (unit, integration from 0026 and from 0022) and CI updates.

**Not in this phase:**

- `organisations`, `org_id`, the hierarchy flag, moving org details: Phase 3.
- Consent, `agg_for`, `actor_type`, `contact_extra`, `invite_id`, the enum rename: Phase 4.
- The operator tool `scripts/user-org-migrate.sh` is its own PR in the train (§7.3). Phase 2 ships the SQL it runs and the boot guard it satisfies.

## 1. Migration `0027_users.sql`

The same frame as 0025/0026:

- save and restore `lock_timeout` / `statement_timeout`;
- `pg_advisory_xact_lock(hashtext('aggregator-dpg:0027_users'))`;
- run as the owner of `aggregators` (`SET LOCAL ROLE`, or refuse), with `RESET ROLE` at the end;
- counts-only messages.

Every step is guarded so a re-run is a no-op. Steps that read a column a later step drops (U11–U13) run inside `DO` blocks gated on `information_schema.columns`, so they are skipped, not parse errors, on a re-run (R5). In practice a re-run never happens, because `apply` and boot both go through drizzle, which records the file. **Journal `when` = `1791200000000`**: above both the old `app_user` values (A24) and 0026.

### 3.4 Coordinator identities

There is no subject for coordinators in the database at 0027, and nothing requires one in Phase 2. They are filled:

1. on the next review-link open or approved request (§3.3);
2. by the train tool's `enrich` step: `findByAttribute('aggregator_id', users.id)` for each coordinator without a `keycloak` identity.

Phase 5 (login by identity) is gated on the `enrich` report being clean.

## 4. Guards in `apps/api/src/db/migrate.ts` (revised after review R2–R4, R15)

| Guard                            | Where                                                                                                                                                               | Rule                                                                                                                                                                                                                                                                                                                                                         | Effect                                                                                                                                                                                                                                                                                                                       |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Foreign migration** (A24, F17) | `runMigrations()` **and** the tool's `apply`, before `migrateWithLock`                                                                                              | **Refuse** a row in `drizzle.__drizzle_migrations` whose `created_at` is **not** any journal `when`: e.g. the abandoned `app_user` rows at `1791000000000` / `1791100000000`. A **hash mismatch on a known `when` only logs `warn`**: migrations 0004, 0008 and 0011 were edited after their first commit, so instances legitimately hold older hashes (R4). | A dev DB with the abandoned migrations stops with a message naming the rows and the fix (`fix drop-app-user`, or recreate it). Existing instances are never blocked by history.                                                                                                                                              |
| **Boot guard** (A4, E8)          | `runMigrations()` **only** (the boot path and `pnpm db:migrate`). **Not** `migrateWithLock`, which the tool's `apply` and the integration tests call directly (R3). | Refuse when **all** hold:<br>1. the pending set includes a **train** migration (journal `when` from 0023's up to the train's last);<br>2. the database is **non-empty**: any row in the coordinator table, `aggregator_orgs`, `registration_invites`, or `contact` when it exists (R15);<br>3. `ALLOW_TRAIN_ON_BOOT` is not `true`.                          | Pods (`RUN_MIGRATIONS_ON_BOOT=true`) exit with a clear message until the operator runs `user-org-migrate.sh apply`; nothing is applied. **Once the train is applied, condition 1 is never true again**, so later releases (0030+) migrate at boot as usual (R2). A fresh, empty DB, such as CI's, migrates at boot as today. |
| **Dev override**                 | env `ALLOW_TRAIN_ON_BOOT=true`                                                                                                                                      | Read once at startup; logged at `warn` when it lets the train run.                                                                                                                                                                                                                                                                                           | Developers' and the e2e stack's databases (e.g. the local `aggregator` DB at 0026) can still move forward while the tool's PR is pending (R3). It is never set in deployment templates.                                                                                                                                      |

**No marker table.** Drizzle runs the pending files in its own transaction (`pg-core/dialect.js`, `session.transaction`), so the tool cannot add a statement to it. After a successful `apply` nothing is pending, so the guard has nothing to check (R3). `train_apply_marker` is removed from the design.

Both guards are unit-tested with a fake executor, and get one integration case each (refused, allowed when empty, allowed with the override, silent after the train).
