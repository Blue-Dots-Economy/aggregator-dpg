# Handoff: inputs for the RBAC work after user & org Phase 5

**For:** the RBAC work (#805 design, #849 implementation, branch `feat/805-rbac`; epic bluedots-program#33).
**From:** user & org refactor Phase 5 (its PR description carries the design decisions R1–R14, P5-1–P5-15 and corner cases C1–C18 that the ids below refer to).
**Agreed 2026-10-07:** Phase 5 is implemented first, on its own; RBAC continues on top of it. This file lists what Phase 5 provides and the explicit changes RBAC should make when it rebases. Paths are as of the Phase 5 branch (`refactor/user-org-phase-5-wip`).

## 2. Explicit changes RBAC should make

| #    | Change                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Why                                                                                                                                                                                                                                            |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| H-1  | **Route access for coordinator decisions and invites:** declare `POST /v1/user/decision/:id` and `POST /v1/user/create` (and the emailed `/admin/v1/aggregator-registrations/{read,decision,renew}` routes, while they exist) as **`org.manage`** on the coordinator's organisation — **not `orgs.onboard`**. Keep `orgs.onboard` for `POST /v1/org/decision/:id` (and `/admin/v1/orgs/*`).                                                                          | Appendix A of `rbac-design-aggregator.md` maps coordinator review to `orgs.onboard`, which the Aggregator PermissionSet does not hold; at R2 every aggregator owner would lose coordinator approval — the main thing the Phase 5 console does. |
| H-2  | **Declare the Phase 5 routes** in `route-access.ts` (list in §1). Suggested: `user/read/me` = any signed-in user; `user/read/:id`, `user/search` = `org.manage` (reach-limited) + `contact.unmask` audited; `user/metadata/update` = `org.manage`; `org/read`, `org/search` = `org.read`; `org/metadata/update` = `org.manage` (name: network admin only); `org/decision` and `org/access/repair` = `orgs.onboard`.                                                  | Phase 5 ships them with its own reach checks; RBAC's snapshot test should cover them.                                                                                                                                                          |
| H-3  | **Adopt or replace Phase 5's actor resolver** behind the `ActorResolverBase` contract; add `grants`. Remove the duplicate if both exist after the rebase.                                                                                                                                                                                                                                                                                                            | One resolver; Phase 5 already answers admin-by-subject.                                                                                                                                                                                        |
| H-4  | **Default org owner ≠ network admin is possible.** Config `DEFAULT_ORG_OWNER_EMAIL` can make another admin the Default org's owner. RBAC assumes they are the same (`rbac-design-aggregator.md:43,77`). Phase 5 treats the Default owner as an ordinary owner of one org (approves its coordinators; cannot invite into or edit the Default org).                                                                                                                    | Align the PermissionSet of the Default org and its owner with that.                                                                                                                                                                            |
| H-5  | **One login = one row** is enforced by Phase 5: a network admin (or Default owner) whose address is a coordinator's is refused by the boot reconcile.                                                                                                                                                                                                                                                                                                                | Same rule as RBAC §6.                                                                                                                                                                                                                          |
| H-6  | **Contact data**: Phase 5 returns contact **plain within reach** (decision P5-8), and logs each single-user read (actor id, target id). RBAC's `contact.unmask` should take over: mask in `user/search` lists, plain only with the capability (audited).                                                                                                                                                                                                             | Phase 5 deliberately left masking to RBAC.                                                                                                                                                                                                     |
| H-7  | **Emailed decision links**: Phase 5 keeps them (secondary to the console deep link); RBAC R2 retires the token pages. Other `ADMIN_EMAILS` entries still review orgs by link only until then.                                                                                                                                                                                                                                                                        | Plan R2 accordingly.                                                                                                                                                                                                                           |
| H-8  | **Grant links**: Phase 5 stops minting 90-day grants (approval, expired-grant recovery and the "already registered" resend all mail a console sign-in link); still-valid grants work until they expire. `POST /admin/v1/invites` can be removed at RBAC R2 or once the longest grant has expired.                                                                                                                                                                    | No new link-token path for RBAC to cover.                                                                                                                                                                                                      |
| H-9  | **Capability failures vs reach failures**: Phase 5 answers **404** for a target out of reach and **403** only when the actor type cannot use a route at all. RBAC's guard should keep 403 for missing capability and leave reach to Phase 5's `scope.ts`.                                                                                                                                                                                                            | No existence oracle.                                                                                                                                                                                                                           |
| H-10 | **Sessions**: role loss ends access through the DB check on every request plus `IdpAdminAdapter.logoutSessions`; the web caches `read/me` for ~60 s.                                                                                                                                                                                                                                                                                                                 | RBAC grant revocation can reuse both.                                                                                                                                                                                                          |
| H-11 | **`aggregator_id` and `decision_made` are admin-only in this repo's realm** (declared in `realm.json`, enforced by `infra/keycloak/init/apply-user-profile.sh`): they are written only by the API's service account. The deployment realm (bluedots-automation) should declare them the same way (handled separately). Once it does, RBAC's resolver can require the recorded login for every coordinator route, as Phase 5's resolver already does for the console. | The database, not a token claim, is the authority for identity.                                                                                                                                                                                |
| H-12 | **An owner whose org is no longer active keeps `org_owner`** until the next role change, so the gate admits them and sends a code before the API answers `403 NOT_ORG_ADMIN`. RBAC's grant revocation (or #851's deactivate) should remove the role and call `logoutSessions`.                                                                                                                                                                                       | Avoids sending codes to ex-owners.                                                                                                                                                                                                             |
| H-13 | **Decision services and `scope.ts` are plain functions** (`services/decisions/*`, `services/authz/scope.ts`), not abstract-class services. RBAC's guard may wrap them as they are, or move them behind a base class if it needs to swap implementations.                                                                                                                                                                                                             | Repo rule `base-class-pattern.md` covers `services/**`.                                                                                                                                                                                        |

## 3. Not done in Phase 5 (RBAC or later)

- Grants (`user_permission_grant`), PermissionSets per org, the OPA sidecar and its enforcement — RBAC.
- Several admins per org, ownership transfer, child orgs, parent move — later phases.
- Deactivate / reactivate — #851. Claim rename `aggregator_id` → `user_id` — #852.
- Contact change with OTP — deferred (needs an SMS sender).
- A database-backed audit table for console actions (today: structured log lines with actor id, target id and field names).
- A Keycloak SMTP / gate probe in `train check` (F19 is DB-only; the runbook checks SMTP and the deployment realm's gate by hand).
- Renaming the org's Keycloak group `display_name` when the network admin renames an org (cosmetic; the group is matched by `org_id`).
