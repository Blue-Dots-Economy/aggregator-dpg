# Plan review (2026-10-06): corner cases, simplicity, duplicates, revert

**Scope:** the plan set of 2026-10-05:

- `user-org-target-model.md`, the map;
- the phase plans `users-phase-2.md`, `organisation-phase-3.md`, `cleanup-phase-4.md`;
- `existing-instance-migration.md`, for deployed instances.

**Method:** checked each design against the code on `feature`, plus an independent reviewer pass over the code paths. Every finding below is already applied to those files; this file records why.

## 1. Data-model simplicity

| #   | Finding                                                                                                                                                                                                                                                                                                                      | Severity | Change made                                                                                                                                                                                                                                                                                                                                                       |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| M1  | **FK cycle.** `users.org_id NOT NULL → organisations` and `organisations.org_owner NOT NULL → users`. A new org and its owner cannot be inserted in either order, and pruning a stale org is blocked by its owner's `org_id`. Admins also needed a heuristic ("newest live org") for `org_id`, which duplicated `org_owner`. | high     | `users.org_id` is the **coordinator's** org only: required for coordinators, NULL for admins (a CHECK). An admin's orgs are `organisations WHERE org_owner = <admin>`. That removes the cycle and the heuristic, and gives each relation **one** home.                                                                                                            |
| M2  | **Admin `status` mirrored the org's status** (it was set from the newest org at backfill and then drifted).                                                                                                                                                                                                                  | med      | `status` / `rejected_at` are **coordinator-only** (registration lifecycle). An admin account has no registration of its own; whether it can log in is the Keycloak user's enabled flag, as today.                                                                                                                                                                 |
| M3  | **`invite_email` copies `registration_invites.email`.**                                                                                                                                                                                                                                                                      | low      | Replaced by `users.invite_id → registration_invites.jti` (`ON DELETE SET NULL`); the email is read through the join. An invite is deleted only with its org, and an org with coordinators cannot be deleted (RESTRICT), so the link survives as long as it matters.                                                                                               |
| M4  | **`tenant_name` copies the parent org's name** for every hierarchy coordinator (the web copies `display_name` into the hidden `name` field) and drifts when the org is renamed.                                                                                                                                              | med      | `tenant_name` becomes **nullable**: it is set only where it differs from the org's name (legacy flat coordinators, now in the Default org). Signals and `org_name` read `coalesce(tenant_name, org.name)`. **This guard matters:** without it, the first-request Signals backfill upsert would rename every formerly-flat coordinator's Signals org to "Default". |
| M5  | `users` mixed admin and coordinator columns with scattered nullability.                                                                                                                                                                                                                                                      | med      | One rule: **an admin row holds only identity** (`contact_id`, `user_type`, `kc_sub`, audit). Every coordinator-only column is listed once, behind one CHECK (target model §2).                                                                                                                                                                                    |
| M6  | **Naming was inconsistent:** enum `aggregator_status`, `aggregator_*` index names, `Aggregator*` stores.                                                                                                                                                                                                                     | low      | Final names: enum `registration_status`; every index, constraint and trigger is `users_*` / `organisations_*`; internal code becomes `UserStore` (with coordinator helpers) and `OrganisationStore`. **API field names, Keycloak attributes and token claims keep `aggregator_*`** (external contract).                                                           |
| M7  | The `legacy_org_details` fallback adds a read-time merge with no end.                                                                                                                                                                                                                                                        | low      | It is implemented once, in the store's SQL (`coalesce(org.x, users.profile->'legacy_org_details'->>'x')`). It retires itself: once an org owner sets a field (Phase 5), the org value wins. `report` counts the remaining fallbacks; when the count reaches 0, a later cleanup drops the key.                                                                     |

## 2. Reads and writes (after the changes)

| Operation                         | Statements, all in one transaction                                                                                                                   | Tables touched |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- |
| Coordinator profile / token check | 1 SELECT: `users ⋈ contact ⋈ organisations` (all PK / FK joins)                                                                                      | 3              |
| Register coordinator              | `linkContact` → INSERT `users` (`org_id`) → INSERT `consent_record`                                                                                  | 3              |
| Register org                      | `linkContact` → `linkAccount(admin)` (reuse or insert) → INSERT `organisations` (`org_owner`) → INSERT `consent_record`                              | 4              |
| Approve coordinator               | CAS `users.status`                                                                                                                                   | 1              |
| Approve / reject org              | CAS `organisations.status`                                                                                                                           | 1              |
| Profile update                    | UPDATE `users` (and `changeContact` for email / phone); org details refused (409)                                                                    | 1–2            |
| Record a login identity           | INSERT `user_identities` ON CONFLICT DO NOTHING                                                                                                      | 1              |
| Prune a stale coordinator         | DELETE `users` (tenant rows cascade, as today; consent links → NULL; contact GC trigger)                                                             | 1              |
| Prune a stale org                 | DELETE `organisations` (invites cascade), then DELETE the owner's admin row **if it owns nothing else and is not the NF admin** (contact GC trigger) | 2              |

No operation needs a deferred constraint, a trigger-maintained mirror or a second write to keep two copies in step.

## 3. Corner cases added to the plan

| #   | Case                                                                          | Handling                                                                                                                                                                                                       |
| --- | ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| K1  | The NF owner's config email already belongs to an org owner                   | The same admin row owns the NF root and their org.                                                                                                                                                             |
| K2  | The NF owner's config email belongs to a coordinator (a contact with a phone) | The contact is reused (looked up by email); a new `admin` row shares it.                                                                                                                                       |
| K3  | No `organisation.root.owner_email` and no `ADMIN_EMAILS`                      | `.invalid` placeholder owner; V6 reports it.                                                                                                                                                                   |
| K4  | Reserved slugs and names                                                      | `default` and the NF slug are reserved in `services/slug.ts`. An existing org that clashes is renamed during the migration (F4).                                                                               |
| K5  | A rejected coordinator re-submits (reclaim) under a different org             | Same `users` row; `org_id` is updated. Earlier tenant rows keep their old `org_id` (it records the org at write time).                                                                                         |
| K6  | A pending org never approved (prune)                                          | It cannot have coordinators (registration requires an active org). Delete it; its invites cascade; the owner row is GC'd per §2.                                                                               |
| K7  | An org with data is deleted                                                   | Blocked: tenant `org_id` and coordinator `org_id` are RESTRICT. Prune only touches pending orgs, which have no data.                                                                                           |
| K8  | A person who is both a coordinator and an org owner                           | Two `users` rows, one contact. A phone or email change on that contact stays refused (D19 `SharedContactError`), as today.                                                                                     |
| K9  | Sessions, queues and links across the window                                  | Unchanged: web sessions hold `aggregator_id` = user id, BullMQ payloads carry the same ids, rate-limit keys use the same ids, public link URLs use `tenant_slug`. **Users stay logged in through the window.** |
| K10 | Migrations 0023 / 0024 (from `feature`) ride in the train                     | 0024 drops the unused `participants` mirror (#819). The revert recreates both tables empty, which is what the 0022 code expects: write-only, no reader.                                                        |
| K11 | `updated_at` drives the prune and cooling windows                             | Every migration step that rewrites rows disables `*_set_updated_at` around it, as 0025 does.                                                                                                                   |
| K12 | An org later made inactive while its coordinators stay active                 | Behaviour unchanged (a coordinator's login does not check its org's status today); revisit in Phase 5.                                                                                                         |

## 4. Seamless, and easy to revert

| #   | Finding                                                                                                                   | Change made                                                                                                                                                                                                                                                                                                                               |
| --- | ------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| V1  | **A snapshot restore after scale-up loses every write made since go-live**, so in practice the plan was fix-forward-only. | **A real `revert`**: `user-org-migrate.sh revert` converts the final schema back to the 0022 shape **keeping post-go-live writes**, so the previous image runs again. It is possible because every removed value has a surviving home (`existing-instance-migration.md` §5). The full mapping is in `existing-instance-migration.md` §13. |
| V2  | A revert that is never exercised will not work on the day.                                                                | A **round-trip test** in CI: fixtures at 0022 → train → revert → compared with the original, with only the listed differences allowed (G14's sub-second `given_at`). Also forward → write new rows → revert → smoke-test the 0022 code. `dry-run` does the same round trip on each instance's clone.                                      |
| V3  | Visible downtime.                                                                                                         | The web stays up and shows its maintenance page; API and worker are at zero for the measured `dry-run` duration plus pod start. Users stay logged in (K9).                                                                                                                                                                                |
